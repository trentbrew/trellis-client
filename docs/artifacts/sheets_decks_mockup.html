Sheets & decks on the graph

Neither one lives inside the editor. The graph owns structure — sheet, column, row, deck, slide — and TipTap is the leaf-level text runtime, leased to whatever cell or region has focus. Three projections, one substrate, one extension vocabulary.

1
Rows are entities. The sheet is a live TQL projection — add a matching entity anywhere in the graph and it appears here. No import, no copy.
2
Formulas store attribute refs, render A1. Toggle it: =C8-D8 is just a view of =this.budgeted - this.spent. Sorting and filtering can never break a reference.
3
The editor lease. Cells render as static HTML; one shared TipTap instance mounts into the focused cell. Mentions, slash commands, embeds work in cells with zero new extension code.
4
Columns can be relations. Owner is a → person edge, not a string — so agents and TQL can traverse it.
5
Aggregates reuse the existing engine. $sum, $avg, $percent from useCollectionFormulas, plus a dependency graph for incremental recompute.

03 · Showroom

A deck is an ordered relation of slide entities

Reorder is a graph op. History is per slide. Regions inside a slide are TipTap fragments — and a region can be a live query, so the deck updates itself.

8
Slides are entities. The deck is an ordered relation — reordering, duplicating across decks, and per-slide history are graph ops on the op-log, not tree surgery on one big document.
9
Every text region is a TipTap fragment. Titles, bullets, speaker notes — same extensions as docs and cells: mentions, embeds, inline comments.
10
The traction slide is a live query. A queryView region — the pitch deck's metrics update themselves. No deck tool can do this without a graph underneath.
11
One slide, four vantages. Thumbnail, sorter, editor, projector are the same component rendered at different vantage levels — this is what fractal responsiveness is for.
