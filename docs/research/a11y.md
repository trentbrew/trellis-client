# Accessibility by Nature 🌟

Yeah, this is actually a profound point that I hadn't fully articulated. Let me think about why Trellis's architecture is inherently accessible.

---

## What Makes Trellis Accessible

### **1\. Separation of Data and Presentation**

**Traditional apps:**

```
Notion → Proprietary UI + Data locked together
Excel → Spreadsheet paradigm baked into data model
Figma → Canvas-centric, visual-first
```

**If you can't see/use the canonical interface, you're locked out.**

**Trellis:**

```json
{
  "nodes": [
    { "@id": "task/website-handoff", "status": "done", "assignee": "trent" }
  ]
}
```

**The data is just JSON-LD.**

**Projection can be:**

- Visual (kanban board)
- Textual (markdown list)
- Audio (screen reader)
- Tactile (braille display)
- Voice (conversational interface)

**Same data, infinite accessibility modalities.**

---

### **2\. Multiple Projections = Multiple Access Modes**

**Example: Budget graph**

```json
{
  "projections": {
    "dashboard": {
      "component": "BudgetDashboard.svelte", // Visual charts
      "a11y": "high-contrast",
      "keyboardNav": true
    },

    "table": {
      "component": "Table.svelte", // Screen reader friendly
      "a11y": "aria-labels",
      "semanticHTML": true
    },

    "summary": {
      "component": "TextSummary.svelte", // Plain text
      "a11y": "text-only",
      "tts": true // Text-to-speech optimized
    },

    "voice": {
      "component": "VoiceInterface.svelte", // Conversational
      "a11y": "audio",
      "stt": true // Speech-to-text
    }
  }
}
```

**User chooses** based on needs/context:

- Low vision → High contrast dashboard
- Blind → Table projection with screen reader
- Hands busy → Voice interface
- Low bandwidth → Text summary

**One graph, many ways to access.**

---

### **3\. Semantic Structure (Not Visual)**

**Traditional design tools:**

```html
<!-- Figma/Canva output -->
<div style="position: absolute; left: 100px; top: 200px;">
  <span style="font-size: 24px; color: #333;">Budget: $2000</span>
</div>
```

**Screen reader:** "Budget colon two thousand dollars" **No semantic meaning:** Is this a heading? A data point? A label?

**Trellis:**

```json
{
  "@id": "budget/housing",
  "@type": "BudgetGoal",
  "trellis:title": "Housing Budget",
  "monthlyLimit": 2000,
  "totalSpent": 1800,
  "status": "🟢 On Track"
}
```

**Projection can render with proper semantics:**

```html
<section aria-label="Budget Goal">
  <h2>Housing Budget</h2>
  <dl>
    <dt>Monthly Limit</dt>
    <dd>$2,000</dd>

    <dt>Total Spent</dt>
    <dd>$1,800</dd>

    <dt>Status</dt>
    <dd role="status" aria-live="polite">On Track</dd>
  </dl>
</section>
```

**Screen reader:** "Budget Goal. Heading level 2: Housing Budget. Monthly Limit: $2,000. Total Spent: $1,800. Status: On Track."

**Full semantic context.**

### **4\. Query Interface = Universal Access**

**Visual UI:**

- Requires seeing
- Requires mouse/touch
- Context-specific (different UI per app)

**Query interface:**

```bash
# Text-based (works with any input method)
$ trellis query "What's my housing budget status?"

Housing Budget:
- Limit: $2,000
- Spent: $1,800
- Remaining: $200
- Status: On Track

# Same data, accessible via:
# - Keyboard only
# - Voice input
# - Screen reader
# - Braille display
# - Low vision (large text)
```

**Universal interface.**

### **5\. Plain Text Source = Assistive Tech Compatible**

**Trellis graphs are JSON-LD (plain text):**

```bash
# Can be edited with ANY text editor
$ vim budget.trellis
$ emacs budget.trellis
$ nano budget.trellis

# Works with screen readers
$ cat budget.trellis | say  # macOS text-to-speech

# Works with braille displays
$ cat budget.trellis | brltty

$ voice-to-text >> budget.trellis
```

**No proprietary UI required.**

## Judy Fan Connection

### **Visual Abstraction = Accessibility Strategy**

**Her finding:** People draw differently based on context

- Close context → Detailed
- Far context → Sparse

**Accessibility parallel:**

- High bandwidth (sighted, desktop) → Detailed visual projection
- Low bandwidth (screen reader, mobile) → Sparse text projection

**Same underlying principle: Context-appropriate representation.**

---

### **Depiction vs Explanation Modes**

**Her finding:**

- Depiction: Shows what it looks like
- Explanation: Shows how it works

**Accessibility parallel:**

- Visual projection: Shows spatial layout (for sighted users)
- Semantic projection: Shows logical structure (for screen readers)

**Example:**

**Visual (Depiction):**

```html
<div class="kanban-board">
  <div class="column" style="background: #f0f0f0;">
    <div class="card" style="left: 10px; top: 20px;">Task 1</div>
  </div>
</div>
```

**Semantic (Explanation):**

```html
<section aria-label="Task Board">
  <h2>In Progress</h2>
  <ul role="list">
    <li role="listitem">
      <article aria-label="Task 1">
        <h3>Website Handoff</h3>
        <dl>
          <dt>Status</dt>
          <dd>In Progress</dd>
          <dt>Assignee</dt>
          <dd>Trent</dd>
          <dt>Due</dt>
          <dd>Jan 15</dd>
        </dl>
      </article>
    </li>
  </ul>
</section>
```

**Both represent same data, different modalities.**

## Concrete Accessibility Features

### **1\. Built-in ARIA Support**

**Projections can auto-generate ARIA:**

```typescript
// kernel/src/projection/a11y.ts
export function generateARIA(node: Node): ARIAProps {
  return {
    role: node['@type'],
    'aria-label': node['trellis:title'],
    'aria-describedby': node['trellis:description'],
    'aria-live': node.status ? 'polite' : undefined,
  };
}
```

**Every projection gets semantic HTML for free.**

---

### **2\. Keyboard Navigation (Built-in)**

**Graph view:**

```typescript
// Tab through nodes
// Arrow keys to navigate relationships
// Enter to expand/collapse
// Space to select

const keyboardNav = {
  Tab: () => focusNextNode(),
  ArrowUp: () => focusPreviousNode(),
  ArrowDown: () => focusNextNode(),
  ArrowLeft: () => focusParent(),
  ArrowRight: () => focusFirstChild(),
  Enter: () => toggleExpand(),
  Space: () => toggleSelect(),
};
```

**Works without mouse.**

---

### **3\. Screen Reader Optimization**

**Text-first rendering:**

```svelte
<!-- BudgetProjection.svelte -->
<script>
  export let graph;
  const budgets = query(graph, 'FIND nodes WHERE @type = "BudgetGoal"');
</script>

<!-- Visual users see cards -->
<div class="visual-mode" aria-hidden="true">
  {#each budgets as budget}
    <BudgetCard {budget} />
  {/each}
</div>

<!-- Screen reader gets semantic list -->
<div class="sr-only">
  <h1>Budget Status</h1>
  <ul>
    {#each budgets as budget}
      <li>
        <h2>{budget.title}</h2>
        <p>Spent {budget.totalSpent} of {budget.monthlyLimit}</p>
        <p>Status: {budget.status}</p>
      </li>
    {/each}
  </ul>
</div>
```

### **4\. Voice Interface**

**Natural language queries:**

```typescript
// kernel/src/voice/interface.ts
export async function handleVoiceQuery(speech: string): Promise<string> {
  const intent = parseIntent(speech);

  switch (intent.type) {
    case 'budget-status':
      const budget = await query(
        `FIND budget WHERE category = "${intent.category}"`,
      );
      return `Your ${intent.category} budget is ${budget.status}. 
              You've spent ${budget.totalSpent} of ${budget.monthlyLimit}.`;

    case 'add-expense':
      await createNode({
        '@type': 'Expense',
        category: intent.category,
        amount: intent.amount,
        date: new Date(),
      });
      return `Added ${intent.amount} expense to ${intent.category}.`;
  }
}
```

**Fully hands-free.**

## Why This Matters

### **1\. Legal Compliance (WCAG, ADA)**

**Apps must be accessible.**

**Trellis makes compliance natural:**

- Semantic HTML (WCAG 4.1.2)
- Keyboard navigation (WCAG 2.1.1)
- Text alternatives (WCAG 1.1.1)
- Multiple modalities (WCAG 1.3.1)

**Built into architecture, not bolted on.**

---

### **2\. Edge Cases = Primary Cases**

**Traditional:** Accessibility is an afterthought

**Trellis:** Accessibility is the architecture

- Screen reader users benefit from semantic structure
- **So do search engines** (SEO)
- **So do AI agents** (machine-readable)
- **So do voice interfaces** (Alexa, Siri)

**Accessible = Machine-readable = Future-proof.**

---

### **3\. Universal Design**

**Curb cuts help everyone:**

- Wheelchairs (intended users)
- Strollers, bikes, luggage (everyone)

**Trellis accessibility helps everyone:**

- Screen readers (intended users)
- Voice interfaces (hands-free users)
- Search engines (SEO)
- AI agents (automation)
- Low bandwidth (mobile users)

**Accessible architecture = Better architecture.**

## Comparison

### **Notion (Inaccessible by Design)**

**Problem:**

- Blocks are `<div>` soup (no semantic HTML)
- Drag-and-drop only (no keyboard alternative)
- Visual layout required (no text-only mode)
- Proprietary API (no third-party tools)

**Result:** Screen reader users struggle

---

### **Trellis (Accessible by Design)**

**Architecture:**

- Nodes are JSON-LD (semantic by default)
- Queries work via keyboard (text-based)
- Multiple projections (visual, text, voice)
- Open format (assistive tech can hook in)

**Result:** Screen reader users have first-class experience

## Next-Level Accessibility

### **1\. AI-Powered Descriptions**

**Visual content needs alt text:**

```json
{
  "@id": "sketch/architecture-diagram",
  "@type": "Sketch",
  "svg": "<svg>...</svg>",

  // AI-generated description
  "trellis:description": "Architecture diagram showing API server (rectangle) connected to database (cylinder) via arrow labeled 'queries'. Cache layer (hexagon) sits between them.",

  // Detailed semantic structure
  "elements": [
    { "type": "rectangle", "label": "API Server", "semanticType": "component" },
    { "type": "cylinder", "label": "Database", "semanticType": "datastore" },
    {
      "type": "arrow",
      "from": "API Server",
      "to": "Database",
      "label": "queries"
    }
  ]
}
```

**Screen reader:** Gets full semantic description, not just "image"

---

### **2\. Adaptive Complexity**

**User preference:**

```json
{
  "user:preferences": {
    "cognitiveLoad": "low", // Reduce complexity
    "visualDensity": "sparse", // More whitespace
    "animationSpeed": "none" // No motion (vestibular issues)
  }
}
```

**Projections adapt:**

```typescript
if (preferences.cognitiveLoad === 'low') {
  // Show summary projection (not detailed)
  // Hide advanced features
  // Use simple language
}
```

## The Big Insight

**Accessibility isn't a feature.**

**It's an emergent property of:**

1.  Separating data from presentation
2.  Using semantic structures (JSON-LD, not divs)
3.  Supporting multiple modalities (visual, text, voice)
4.  Enabling queries (universal interface)
5.  Being open (assistive tech can integrate)

**Trellis is accessible because its architecture is sound.**

**This is why it feels right.**
